## 一、结论

**可行，没有做不到的功能。** 发声引擎（`core/`）和界面本来就与独立 App 分开，iPlug2 原生支持 VST3 和 AU。

**真正的工作量在四件独立 App 不需要、插件必须做好的事：**

1. **`OnReset` 的含义不同**：插件里它被调用得很频繁（停止走带、旁路、关闭处理……），现在每次都会重建整台机器。
2. **播放中安全切换整台机器的状态**：DAW 打开工程、切预置时音频可能还在跑；现在的切换方式要求音频已经停下。
3. **插件窗口经常是关着的**：MIDI CC 的旋钮变化现在要靠面板刷新才写进保存状态。
4. **只属于独立 App 的功能要拆开**：屏幕尺寸、金属外壳、重开音频、日志、录音、状态文件。

| 阶段 | 内容 | 工作量（以现在一个 PR 的大小计） |
|---|---|---|
| **第 1 阶段：能用的插件** | macOS 上的 AU（AUv2）+ VST3、Windows 上的 VST3；乐器类型，立体声 WET 输出；音色随 DAW 工程保存和恢复；MIDI 弹奏；界面可缩放 | 约 8–10 个 PR。已完成 |
| **第 2 阶段：像样的插件** | 宿主自动化；跟随 DAW 速度和播放 / 停止；多路输出（DRY A/B 单独出轨） | 实施前核查已开展，细则待决策；拆分建议见第九节 |
| **第 3 阶段：可选** | 音频输入（PREAMP 处理 DAW 里的声音）。~~CLAP；AUv3~~ | 音频输入约 1–3 个 PR。暂时不启动 |

| # | 问题 | 决定 | 技术说明 |

| 3 | 插件里的 REC | **面板保留，点击无效** | 外观和独立应用相同（实施时隐藏会改掉面板，业主否掉了）。`recorderEnabled = false`，REC 按钮和 WET / DRY / ALL 不接收鼠标。`toggleRecording` 在插件里是空函数，不调用 `lunar_host_recordings_dir` / `lunar_host_reveal_dir`。录音用 DAW 自己的录音 |

**AU 格式说明（AUv2 和 AUv3）**
- AUv2 是 Mac 桌面上的主流 AU 格式，Logic、Ableton Live 等都直接支持，不是"过时格式"。插件就是一个放进 `~/Library/Audio/Plug-Ins/Components` 的 `.component` 包。本地签名就能载入，不需要 Apple 开发者账号。第 1 阶段做的就是这个。
- AUv3 主要为 iPad / iPhone 设计。在 Mac 上它也必须装在一个 App 里，以"App 扩展"形式运行，要求沙盒和带权限声明的签名。
- ~~AUv3 留在第 3 阶段，只有将来要做 iPad 版才值得。~~ **AUv3 不做**（业主，2026-10-08）。Lunar 24 只做电脑上的独立 App 和插件，不做能在 iPad 上运行的版本。没有 Apple Developer Program，签不了这种扩展。已经做好的 AUv2 不受这个限制。

**CLAP**
- CLAP（CLever Audio Plugin）是 Bitwig 和 u-he 在 2022 年公布的另一种插件格式，协议公开。Bitwig、Reaper 等能加载它。Ableton Live 加载 VST3 和 AU，不加载 CLAP。
- ~~第 3 阶段可选做 CLAP。~~ 规划时写进去的。业主的宿主是 Ableton，不做 CLAP。

**以后 MIDI 绑定改成随工程保存的代价：不大，约 1 个 PR。**
- 绑定已经有现成的编码 / 解码（`midi_map_encode` / `midi_map_decode`）。
- 第 1 阶段存进工程的数据从一开始就带"格式标记 + 版本 + 分段"的头。以后只是多加一段"MIDI 绑定"，旧工程照样能读（没有这一段就用全局文件）。
- 真正要想清楚的是规则，不是代码：工程里的绑定和全局文件谁优先；在插件里改绑定时写回哪里。

## 三、必须改的地方（按技术点）

### 1. 构建
- 新增 VST3、AUv2 两个构建目标（iPlug2 自带 `iplug_configure_vst3` / `iplug_configure_auv2`），只在 macOS / Windows 上加；Linux 照旧只编引擎和测试。
- VST3 SDK：3.8.0 起是 MIT 许可（已核对官方 LICENSE），与本项目的 Apache-2.0 兼容。不进仓库，CI 按**固定的 3.8.x 版本**下载（iPlug2 下载脚本默认拉 master，不能用默认值）。
- `config.h` 按格式区分：
  - 乐器类型 `PLUG_TYPE 1`；
  - 声道：插件 `"0-2"`；独立 App 分支保持现有 `"0-2 1-2 2-2 0-4 1-4 2-4"` 不变。
  - 插件实际出声（`plugin.cpp` 的 `kPluginInputs` / `kPluginOutputs`，`ProcessBlock`）：引擎固定按 0 个输入、2 个输出准备，这两路是 WET L 和 WET R。DRY A、DRY B 在引擎里照常计算，第 1 阶段不送到 DAW（单独出轨是第 2 阶段）。DAW 接上的输出少于 2 路时，这一块写成静音，不把引擎写进缓冲区。立体声乐器轨会接上两路，听到的是 WET。
  - AU：`AUV2_ENTRY` / `AUV2_ENTRY_STR` / `AUV2_FACTORY` 等宏，类型 `aumu`、子类型 `Lu24`、厂商 `Lua2`（沿用现有编码）；
  - VST3 分类 `Instrument|Synth`；
  - Objective-C 类名唯一前缀，避免同一 DAW 同时载入 AU 和 VST3 时冲突。
- 新文件：`host/resources/Lunar24-AU-Info.plist`、`host/resources/Lunar24-VST3-Info.plist`。
- macOS 只出 Apple 芯片（arm64）版本，和独立 App 一样（CI 的 `macos-latest` 就是 Apple 芯片）。不支持 Intel Mac；DAW 也要以原生模式运行，不能用 Rosetta 模式打开。
- CI：mac / win 作业额外编插件，上传为 Actions 产物（`Lunar24-Plugins-macOS`、`Lunar24-Plugins-Windows`）。独立 App 的产物照旧。

### 2. 把只属于独立 App 的功能拆开
`plugin.cpp` 调用 11 个平台函数，分在三个文件：

| 函数 | 现在实现在哪 | 插件版 |
|---|---|---|
| `lunar_host_avail_logical_w/h`、`lunar_host_screen_scale`、`lunar_host_force_clamp` | `main.mm` / `window_metrics_win.cpp` | 不按屏幕开窗，用固定默认大小（第 6 点） |
| `lunar_host_case_margins`、`lunar_host_place_view` | 同上 | 没有金属外壳，边距为 0，面板铺满窗口 |
| `lunar_host_audio_watchdog`、`lunar_host_request_audio_reopen` | `iPlug_app_host_override.cpp` | 插件没有自己的音频设备：不要看门狗；"重开音频"改用第 4 点的安全切换 |
| `lunar_host_log` | `iPlug_app_host_override.cpp` | 不写 audio.log |
| `lunar_host_recordings_dir`、`lunar_host_reveal_dir` | `main.mm` / `window_metrics_win.cpp` | 插件不调用。面板上的 REC 仍画着，点击无效 |

其它独立 App 功能：

| 功能 | 插件版 |
|---|---|
| Preferences（音频设备、采样率、MIDI 输入） | 不要，DAW 管 |
| MIDI 设备热插拔、自动选择输入 | 不要，DAW 负责送 MIDI |
| 启动读状态文件、30 秒自动保存、退出保存 | **关掉**。插件绝不能读独立 App 的状态文件，否则每个新实例都带着 App 上次的音色打开。改为存进 DAW 工程（第 5 点） |
| MIDI 绑定文件 | 和独立 App 共用全局文件。多个实例同时写时文件不会损坏（整文件原子替换），后写的覆盖先写的 |
| 菜单栏 About | 插件没有菜单栏；版本号和 Build 号显示在 MIDI 设置面板右下角（已做） |
| 面板上"NO AUDIO（见 Preferences）"提示 | 插件版换成不提 Preferences 的说法 |

**做法**：只属于独立 App 的代码用 `#if APP_API` 隔开，独立 App 编译出来的代码和现在一致；插件专用实现放新文件，不改 `main.mm`、`iPlug_app_host_override.cpp`、`window_metrics_win.cpp`。

### 3. `OnReset` 规则
- 现在：`OnReset` 每次都做完整 `engine_.prepare()`（重建整台机器，实测约 2.5 ms，会分配内存），还会读一次状态文件、处理 RESET PANEL。
- 插件里 iPlug2 调用它的场合：
  - AU：设置采样率、设置最大块大小、宿主发 Reset（Logic 在走带跳转、停止等时候会发）、旁路切换（`IPlugAU.cpp` 1169 / 1222 / 1237 / 2448 行）；
  - VST3：`setupProcessing` 和每次关闭处理（`IPlugVST3_ProcessorBase.cpp` 228 / 236 行）。
- 照搬的后果：每按一次停止，嗡鸣、效果器尾音、琶音器都从头开始；有的宿主发 Reset 时音频还在跑，变成实时安全问题。
- 插件版规则：
  - 采样率、最大块大小、声道配置**任一真的变了**：才完整重建（这些情况下宿主保证音频已停）；
  - 其它 Reset：只通过现有实时队列放掉按住的音、清掉延音踏板，不重建、不分配内存。
- 独立 App 的 `OnReset` 不变。

### 4. 播放中安全切换整机状态（方案 A）
- 现状：`commit_()`（`standalone_audio_engine.h:1024`）直接替换引擎内部的 `definition_` 指针，并假设音频线程已停；界面线程也直接写这个对象里的状态。DAW 打开工程或切预置时走这条路，音频线程会读到已释放的内存。
- 方案 A：
  1. 界面线程在后台把新状态解码、校验，并建好新的整机；
  2. 请求切换；音频线程在下一个块做几毫秒淡出，然后进入"静音、不碰整机"的状态，并回应"已停"；
  3. 界面线程看到回应后换上新整机，旧的由界面线程释放；
  4. 音频线程淡入恢复。
- 两条线程只通过原子变量交接，音频线程不等待、不加锁、不分配内存。界面线程等回应时设上限（例如宿主不在处理音频、音频线程根本不跑的时候），超时说明音频没在跑，可以直接切换。
- 同一个机制解决：DAW 载入工程 / 预置；插件里的 RESET PANEL（现在靠 `lunar_host_request_audio_reopen()` 重开音频，插件做不到）。独立 App 的 RESET PANEL 也改用它，不再重开音频。
- 专门测试：切换过程音频线程不分配内存（复用现有分配探测测试的写法）；在另一个线程持续出声时反复切换，不崩、无非法数值；切换前后状态一致；在 ASan + UBSan 下跑；再加一个 ThreadSanitizer 跑法检查数据竞争。

### 5. 音色随 DAW 工程保存
- 实现 `SerializeState`（编码当前整机状态写进工程）和 `UnserializeState`（解码 → 迁移 → 校验 → 交给第 4 点的切换）。
- 数据带"格式标记 + 版本 + 分段"的头，以后加段（例如每工程的 MIDI 绑定）时旧工程还能读。
- 数据损坏或校验失败：保持当前音色，不崩。
- 解码和建整机只在非音频线程做。

### 6. 插件窗口
- 默认大小约为面板的一半（接近现有最小尺寸 1216×836），可缩放并保持比例。先给几档固定大小，在 Ableton 里测稳后再开放自由拖动。
- 没有金属外壳。REC 按钮和 WET / DRY / ALL 照面板画，点击没有反应。没有 Preferences。
- 窗口关闭再打开时面板重建；面板自身状态（键盘菜单页、MIDI 学习状态）随窗口重置，音色不受影响。

### 7. 插件窗口关着时的状态写回
- 现状：MIDI CC 带动的旋钮变化、MIDI 绑定触发的卡带和预置切换，在面板显示刷新里（`panel_editor.h:1720`，`syncParametersFromAudioThread`）写回保存状态。
- DAW 里插件窗口多数时候关着：这些变化存不进工程，长度 256 的音频→界面队列会被塞满。
- 改法：挪到 `OnIdle`（iPlug2 插件不开窗口也有 `OnIdle` 定时器）。面板刷新只负责重画。独立 App 一起改，行为不变。

### 8. 电脑键盘弹奏
- Ableton 自己有电脑 MIDI 键盘，按键一般被它拿走；插件窗口里用 A W S E D… 弹琴板不可靠。
- 插件里弹奏走 DAW 的 MIDI 轨道；鼠标点琴板、拧旋钮不受影响。MANUAL_TESTS 写明，不当作 bug。

- DRONE VOICES 的开关也存进工程（分段 `KEYS`），重开工程和保存时一样在响；独立 App 仍然每次启动都关着。
- 共用 MIDI 绑定的前提：App 里 Learn 会记下设备名，插件不知道 MIDI 来自哪个控制器。插件里改为"任何设备的绑定都算数"，否则 App 里学的绑定在插件里全部失效。
- 独立 App 的状态文件和插件的工程数据共用同一个读取函数（`restore_saved_state`），旧格式升级和修补只有一份。
- VST3 和 AUv2 编的是同一份 `plugin.cpp` / `plugin.h`。声音、面板、MIDI、工程数据格式没有两套。唯一的格式分支：状态块读坏时，AU 返回 0（它的包装层把 0 当成"没恢复"），VST3 返回已经读过的字节数（后面紧跟着宿主自己的 bypass 标志）。正常存档两条路相同。

### 8.1 总体判断：基本演奏录音能力已具备，完整重演与验收要分开看

**可以暂时冻结第 2、3 阶段，把当前版本作为“在 DAW 中演奏、实时录成音频的立体声合成器”使用。第一阶段已经建立这条基本能力链，不需要完成后续阶段才能开始创作。**

必须区分两个结论：

- **演奏并把当场声音录下来：当前能力基本齐备。**

### 8.3 工作流一：实时演奏并录成音频

一个完整例子：**打开两个 DRONE → 弹 VCO → 慢慢改变滤波 → 操作光敏头 → 切换效果 → 收尾。**

当前版本可以在 DAW 里发出这些声音。把输出送到一条音频轨实时录制，就能保留整段表演，包括：

- 鼠标和 MIDI 控制带来的音色变化；
- DRONE 的开关和持续演化；
- 光敏头、接线、效果器变化产生的声音；
- 混响和延迟的实际尾音。

**这条工作流不需要插件宿主自动化、不需要 DRY 多输出，也不需要第三阶段的音频输入。** 插件负责输出声音，DAW 负责把声音记录为音频文件，所以插件面板 REC 点击无效并不形成录音能力缺口。

Ableton 官方专门介绍了这种方法：对于一个音符就能产生复杂演化声音的乐器，直接录音频有时比记录输入 MIDI 更适合后续编辑。参见 [Recording MIDI as Audio](https://www.ableton.com/en/live-manual/12/routing-and-i-o/#recording-midi-as-audio)。

Live 里的典型设置：

1. MIDI 轨加载 Lunar 24，负责演奏和发声；使用外部键盘时正确选择输入并开启监听／Arm。
2. 新建音频轨，`Audio From` 选择 Lunar 所在轨。
3. 选择合适的取声位置，例如 `Post FX`。该位置也会包含 Lunar 后面的轨道效果；如果需要只录 Lunar，要据实际设备链选择取声点。录音轨监听设为 `Off`，由原乐器轨监听，避免重复听到。
4. 给音频轨开启录音，演奏结束后保留足够尾音，再停止。

录好后，这段音频可以剪辑、编排、淡入淡出、加效果、混音和导出。重新打开工程，已录音频本身不会因插件自由运行状态改变。

代价是保留了**表演结果**：之后不能单独修改“当时第 12 秒滤波旋钮转了多少”，而要重新演奏或处理已录音频。对于 ambient、drone、声音设计，这是正常且可以正式使用的创作方式，并非临时凑合。仍应通过一次实际录音验证具体宿主路径。

### 8.4 工作流二：录 MIDI、编辑音符、再回放

一个完整例子：**先调好音色 → 用 MIDI 键盘弹奏 → 录 MIDI → 修改音符 → 回放。**

当前架构具备这条能力。DAW 把录到的音符重新交给插件，插件通过与实时演奏相同的 `ProcessMidiMsg()` 入口处理；音符事件带有块内时间位置，通过 `enqueueEventFromAudioThread()` 转为引擎的绝对采样时间。代码见 [host/plugin.cpp](../host/plugin.cpp)、[StandaloneAudioEngine](../host/include/host/standalone_audio_engine.h)。

**普通音符跟随 DAW 时间线，不依赖第二阶段的“宿主时钟同步”。** 钢琴卷帘里第 3 小节的音符由 DAW 在对应位置发送；第二阶段同步主要解决插件**内部** ARP／SEQ 如何跟随宿主速度和走带，两者不是同一个问题。

必须区分 DAW 记录的内容：

| 实际操作 | 当前可留下什么记录 |
|---|---|
| 外部 MIDI 键盘、Ableton 电脑 MIDI 键盘发来的音符 | 可以录进 MIDI 片段，再编辑音符与时值 |
| 外部控制器发来的 CC、弯音等 | DAW 可以记录；插件是否按预期重现，还取决于映射、初始状态和消息传递 |
| 鼠标拧插件旋钮、点击 DRONE、拖接线、操作光敏头 | 当前不会自动录成插件参数自动化；实时录音频可保留声音结果 |
| 鼠标点击插件触摸键盘／插件自己处理的电脑键盘演奏 | 直接进入内部引擎，当前不向 DAW 输出 MIDI，不能指望自动留下 MIDI 音符 |
| 插件内部琶音器／音序器生成的音符 | 没有 MIDI 输出，不能直接录成其生成结果的 MIDI 片段；输入和弦与内部生成音符不是同一份数据 |

[host/config.h](../host/config.h) 声明 `PLUG_DOES_MIDI_IN 1`、`PLUG_DOES_MIDI_OUT 0`；面板演奏在 [panel_editor.h](../host/panel_editor.h) 中直接向引擎发送事件。

所以“录音时确实听见变化”不等于“变化已经成为以后能自动重放的数据”。**满意的表演同时录一条音频，最能避免丢失结果。** MIDI 轨记录输入、音频轨记录输出，是两种可以并行使用的记录方式。来源：[Ableton 官方：录制新片段](https://www.ableton.com/en/live-manual/12/recording-new-clips/)。

### 8.5 实质限制之一：内部参数变化不能作为宿主自动化重演

例如录了 8 小节 MIDI，期间用鼠标把滤波从暗转亮。保存工程保存的是旋钮的**当前位置**，不是这 8 小节的变化过程；再次回放不能期待它自动从暗转亮。要保存变化过程，需要录音频，或以后实现相应参数的宿主自动化。

这会影响常见编曲方式，但不阻止实时录音。对经常在时间线上编曲的人，滤波、音量、效果混合量自动化很日常，不能把它统称为罕见的高级需求。

当前仍能使用 DAW 轨道音量、声像、发送量自动化，插件后面的效果器自动化，以及已录音频的剪辑和淡入淡出。这些能完成不少编曲工作，但不能等价替代 Lunar 内部的全部变化。

MIDI Learn 也不能笼统当作宿主自动化的完全替代：DAW 可以把控制器消息录入 MIDI 片段，但必须让消息真正进入轨道，而不是被控制器脚本拿去做宿主遥控。当前 MPK 的用户预设可走插件 Learn；PLUGIN／DAW 模式下部分旋钮被 Ableton 脚本接管，而 Lunar 尚未公开对应宿主参数，因此拧旋钮可能不起作用，具体已记录在 MANUAL_TESTS 第 17 节。

相对旋钮、按一次切换状态的按钮／DRONE 绑定还依赖起始值：同一串“增加一格”或“翻转一次”消息，从不同初始状态开始结果会不同。保存表演结束时的值，再从头回放这些动作，不必然重建原来的开始状态。因此“已录了 CC／打击垫”不等于“整场操作一定准确重演”。

### 8.6 实质限制之二：内部节奏、持续声音与 DAW 走带的关系

当前内部 ARP／SEQ 没有建立正式的宿主时间同步关系。把两边 BPM 手动设成一样，也不保证同一拍开始、循环回到同一步、跳转后对齐或变速后仍一致。现有 MIDI clock 入口不等于已经具备宿主时间线同步；不能假定 DAW 会通过普通插件 MIDI 轨传入完整的时钟／走带消息。

对不同用途的影响：

- 自由演奏、持续音、环境纹理：通常可以接受内部自由运行。
- 需要和鼓点严格锁定的内部琶音／序列：这是明显限制。
- 普通键盘模式下，由 DAW MIDI 片段安排节奏：可以绕开内部时钟问题。
- 用 DAW 的琶音器生成 MIDI，再送进 Lunar 的普通键盘模式：也是现有可选方式，但与 Lunar 自己的 ARP 行为不完全相同。

DRONE 在 DAW 停止后继续响，是 T17.3 已验收的既定行为，不是“停止失效”。需要整段声音退出时，可用 DAW 音量／静音或已录音频控制。插件收到宿主 Reset 时会释放键盘演奏状态；不能把这与普通按下 Live 停止按钮的实际行为混为一谈。

工程恢复的是机器配置和专门保存的 DRONE 开关，不是每个振荡器相位、正在运行的和弦、效果延迟缓存或整个过去的声音历史。自由运行／随机演化声音回放不要求逐采样相同；若必须保留当次结果，应记录音频。

### 8.7 MIDI 方案属于使用者，不随 DAW 工程保存

业主于 2026-10-10 明确：独立 App 与插件必须共享 MIDI 方案库，Learn 绑定与使用习惯不放进作品工程。这是产品选择，不作为待修复缺陷或后续工程归档任务。

每套命名方案包含绑定及 CHANNEL、TRANSPOSE、VELOCITY、SPLIT，保存在设置目录的 `midi-profiles/`。各实例持有自己的当前方案；打开列表／选择时读取已保存内容，不广播强制切换。启动读取上次选择；DAW 工程载入只恢复机器状态与 DRONE 开关，不改 MIDI 方案。旧单套开发配置不迁移。

同一 MIDI 片段的音高、力度与分区仍由当前方案解释；需要相同演奏方式时由使用者选择相同方案。代码见 `MidiMapStore`、`useMidiMapDirectory_()` 与 `PluginProjectState`。

“关窗改 CC 再保存”已经通过 T17.6；但 `SerializeState()` 当前读取 canonical state，MIDI 改值由 `OnIdle()` 异步同步，刚改值就立刻保存的时间边界还值得补查。不能把一般流程通过等同于对每个保存时序都已有保证，也不能未经线程分析就让保存回调直接并发排空队列。

### 8.8 实质限制之四：离线导出、冻结与尾音声明

**导出和冻结属于基础制作可靠性，不能因为不是现场弹奏就归入高级可选功能而忽略。**

当前 `processAnyLength()` 能把较长宿主音频块拆成引擎接受的大小；[test_host_engine_oracle.cpp](../tests/host/test_host_engine_oracle.cpp) 的 `long_block_split()` 验证拆块一致性、落在后续子块的 MIDI 音符和无分配。因此不存在“只会实时发声，结构上完全无法参与离线处理”的明显缺口。

但这不证明 Ableton 的离线导出、冻结、转音频已全部通过。原生宿主可能采用不同的处理节奏、块大小、Reset 和尾音策略，当前第 17 节没有单独记录这些结果。

本次确认了一个声明与声音行为不符的问题：

- Lunar 没有设置尾音长度；
- iPlug2 的 `mTailSize` 默认是 0，见 [IPlugProcessor.h](../third_party/iPlug2/IPlug/IPlugProcessor.h)；
- VST3 的 `getTailSamples()` 和 AU 的 `kAudioUnitProperty_TailTime` 会把这个值报告给宿主，见 [IPlugVST3.cpp](../third_party/iPlug2/IPlug/VST3/IPlugVST3.cpp) 和 [IPlugAU.cpp](../third_party/iPlug2/IPlug/AUv2/IPlugAU.cpp)。

所以插件实际有包络释放、混响、延迟，却向宿主报告尾音长度为零。Steinberg 说明宿主可用尾音信息决定离线处理、处理优化和避免声音截断；来源：[IAudioProcessor::getTailSamples](https://steinbergmedia.github.io/vst3_doc/vstinterfaces/classSteinberg_1_1Vst_1_1IAudioProcessor.html)。

**可以确认声明不符，不能直接断言当前 Ableton 已因此截尾。** 不同宿主／导出方式可能有不同处理；实时录音在 DAW 持续处理且录音长度足够时也与自动尾音推断不同。应先核查实际效果，再决定适合持续 DRONE 和有限／长效果尾音的声明策略，不在本次直接把某个固定秒数或无限尾音当作已定修复。

这是第一阶段基础兼容性核查和必要修补，不需要为它启动整个第二阶段或升级整个 iPlug2。

### 8.9 哪些缺少的能力不构成基本乐器用途的重大缺口

- **只有 WET 立体声输出**：不能同时单独取得 DRY A/B，但仍能正常演奏、录制、加效果和混音；多输出按需要选择即可。现有 DRY 也不是全机干声或六个 DRONE 的分轨，详见 9.9。
- **没有外部音频输入**：不能把 DAW 的外部声音送入 PREAMP／内部处理路径，但这扩展的是声音处理器用途，合成器插件并非必须具备。
- **没有 MPE、没有内部生成 MIDI 输出**：属于明确能力边界，不能单独据此断言整个乐器插件不完整。若目标就是导出内部琶音 MIDI，则 MIDI 输出会变成该工作流的必要条件。
- **没有插件内部录音器**：DAW 已负责录音；REC 留在面板但点击无效是既定产品选择，应让使用者知道用 DAW 录。

### 8.10 一般成熟合成器插件做到什么层次

**常见成熟产品通常更接近“第一阶段，加上第二阶段中的参数自动化和必要的节拍同步”，但不意味着必须包含本项目第二阶段的所有内容。** 原计划把必要程度不同的工作放在了同一个阶段，不宜仅按阶段名称判断价值。

| 能力层次 | 常见内容 | 对当前 Lunar 的意义 |
|---|---|---|
| 基础乐器能力 | 加载、演奏、输出音频、保存恢复、多实例、可靠录制和导出 | 第一阶段主体已完成；录制／导出验收需补齐 |
| 常规 DAW 编曲能力 | 常用参数自动化；有节奏功能时提供宿主同步；常用控制器映射 | 对成熟通用合成器很常见，当前有明显差距 |
| 按定位提供的扩展 | 多路输出、外部音频输入、MIDI 输出、MPE、复杂走带定位等 | 可以长期按产品用途取舍 |

这是一种产品分析，不是插件标准规定的官方等级，也不是对所有产品的统计结论。参考例子：

- **Diva** 有宿主自动化和宿主同步的调制／效果；官方明确说明部分开关因技术原因未开放自动化。成熟插件也可以选择性开放参数，不必把每种操作都自动化。[Diva 官方手册](https://u-he.com/downloads/manuals/plugins/diva/Diva-user-guide.pdf)
- **Surge XT** 提供宿主节拍同步、MIDI Learn 和与宿主自动化相关的操作入口。这些能力也常见于成熟开源产品。[Surge XT 官方手册](https://surge-synthesizer.github.io/manual-xt/)
- **Ableton** 把插件参数配置、映射和自动化作为日常流程介绍，同时说明插件没公开的参数无法加入宿主面板。[Plug-In Configure Mode](https://www.ableton.com/en/live-manual/12/using-plug-ins/#plug-in-configure-mode)

因此不能把整个第二阶段统称为“高级能力”：自动化对一般编曲很常规，有节奏功能时宿主同步也很常用；多输出、外部音频输入则更取决于用途。反过来，“常见产品通常有”不等于“Lunar 现在必须做”。若主要是手动演奏、声音探索、音频采集，第一阶段已能提供实质创作价值。

### 8.11 如暂停新增功能，建议保留的基础验收与维护

**可以冻结第 2、3 阶段，但保留第一阶段的基础使用验收和缺陷修复。** 暂停新增能力，不应意味着遇到保存、录音、导出问题也不处理。下表是建议，未实施、未验收，不是重新开启后续阶段的授权。

| 补充检查 | 做什么 | 要确认的结果 |
|---|---|---|
| MIDI 录制与回放 | 用固定音色录普通键盘演奏，包含长短音和弯音（无踏板硬件，不要求踏板验收）；保存重开再回放 | 音符与常用表情正常，音色正确，无漏音／挂音；记录实际使用的 MIDI 方案及其设置 |
| 实时录音频 | 录一段含 DRONE、鼠标旋钮、光敏头和效果尾音的表演；关闭原插件发声，只听录音 | 当场的声音变化已完整留在音频中，未误把只录 MIDI 当成录到全部表演 |
| 导出和冻结／转音频 | 检查开头、最后一个音和混响尾部；覆盖 MIDI 驱动声音和持续 DRONE，按具体 Live 版本使用相应命令 | 无无故空白、漏音或截断；自由运行声音不要求逐采样完全相同；核实尾音声明影响 |
| 工程重现边界 | 核对 MIDI 方案切换对旧工程演奏的影响；控制器改值后保存重开，包含刚改完就保存 | 分清工程自身保存的状态、全局依赖和保存时序；必要问题单独修补 |

这些检查不要求重写核心引擎，也不要求开启自动化、时钟同步或多输出。现有验收结果继续有效；补齐的是原先没有明确覆盖的实际制作流程。Windows 手测取消的决定不因这张建议表自动改变。

### 8.12 第一阶段切换静音断言的 quick check 结论（保留上下文）

此前 Linux 并行运行 67 项测试时，`test_state_swap` 出现过 `st.lastBeforePark < 1e-12` 失败；单独连续运行 20 次通过。业主要求只快速走读，不开展复杂测试，也不因未证实的问题阻止后续讨论。

走读结论：正常音频持续回调路径中，淡出完成确认与 `AudioScope` 的线程交接没有发现明显缺陷。另有无回调超时路径（约 `20 ms + 3 × blockMs`，256／48 kHz 时约 36 ms；另有 500 ms 上限），可能在最后一个已输出块尚未完全淡到零时进入停放；替换机器前仍等待音频临界区退出。测试使用带 sleep 的模拟音频线程，却无条件要求停放前最后样本已经为零，没有区分超时路径。

### 9.1 第二、第三阶段的原始设想（迁移保留，不是当前实施决定）

以下三段来自原第三节第 9–11 点，仅移动位置并调整标题层级，正文保留。它们写于本次深入核查之前，其中“始终跟 DAW”“宿主 ID = 内部 ID”“开关辅助输出就重建”等仍需按后文修订或决策；不能直接照旧施工。第三阶段的 AU 类型／VST3 输入方案也只是原始候选，不表示已完成宿主兼容性验证。

#### 原第三节第 9 点：DAW 的速度和走带（第 2 阶段）

- 引擎已通过 `ControlEventKind::clock` 事件接收外部节拍（现在来自 MIDI 时钟或 CLOCK 插孔）。
- 插件版每个块读 iPlug2 提供的速度、播放位置（PPQ）和播放状态，算出本块内每个节拍的样本位置，生成同样的时钟事件；播放开始对齐小节，停止时停下。

#### 原第三节第 10 点：宿主自动化（第 2 阶段）

- 先定**对外参数清单**：面板旋钮、开关、选择开关；不含键盘菜单内部项和效果器程序内部参数（注册表共 349 个参数）。清单写进 `spec/machine/lunar24.json`，由生成器产出。
- 宿主参数编号 = 注册表数字 id，永久不变；加测试防止编号被改。
- 名称带模块前缀（例如"VCO A Tune"，现在多个参数都叫"Tune"）；选择开关按档位离散化；旋钮用现有旋钮曲线（`knob_to_value`）映射。
- 双向同步：DAW 改参数走现有实时队列，面板跟着动；面板拧旋钮通知宿主（开始 / 数值 / 结束），DAW 能录自动化。

#### 原第三节第 11 点：多路输出与音频输入（第 2–3 阶段）

- 引擎已有 WET L/R + DRY A/B 四路输出。第 1 阶段的主输出已经是立体声 WET（第一节）。第 2 阶段把 DRY A/B 做成一组辅助输出。DAW 开关辅助输出会改变声道数，按第 3 点"声道配置变了"处理。
- PREAMP 接 DAW 的声音：做成带输入的乐器（AU 的 music effect 类型、VST3 的侧链），放在最后按需做。

### 9.2 iPlug2 版本机制、全局维护与升级取舍（问题 1、4）

**结论：当前固定版本的机制本身没有发现全局性错误；自动化精度限制不能归因于项目落后于上游。** 2026-10-08 查询官方远端默认分支 `master`，其 HEAD 与项目锁定提交同为 `d54f69050f517e43b941d88c2a170f0a840b9ee4`（提交日期 2026-08-19）。这是当时的查询结果，不保证未来上游仍停在该提交。

此前“iPlug2 版本问题”的表述容易让人理解成用了旧框架，应更正为：**当前锁定源码存在特定能力边界，而当时没有更新的官方默认分支版本可以一键解决。** 查询到的 `VST3/paramqueue` 是 2021 年的旧开发分支（`d46c5695`），不是更晚的稳定发行，也没有切换项目去使用它。

以下保留先前全局维护讨论的全部要点：

- 自动化、DAW 同步和 DRY 辅助输出是三项可独立取舍的增强能力，均不是第一阶段插件可用的前提。“必须处理”的技术项是采用对应功能后的要求，不表示必须实施整个第二阶段。当前讨论先确定创作需求、收益和风险，再决定功能及精度范围。
- iPlug2 使用 Git 子模块锁定准确提交，CI 递归检出；VST3 SDK 另固定 `v3.8.1_build_84`。这种机制有利于稳定，不会自动跟随上游漂移；它不等于锁定操作系统、编译器和全部构建环境。`IPLUG2_DIR` 允许本地指定另一源码路径，发布构建应确认实际路径和版本。
- 独立 App 已替换上游 `IPlugAPP.cpp` / `IPlugAPP_host.cpp` 两个实现文件；后者有较多设备、MIDI 和状态保存定制。未来框架升级应单独成 PR，检查这些定制与新框架头文件/生命周期/构建脚本的兼容性。现有 CMake 门禁只检查选中了替代源文件，不能证明定制与上游差异仍符合预期；文件注释引用的 `check_host_override_drift.py` 已删除，不能把旧注释当成现有保障。
- 当前没有比项目更新的官方默认分支提交可用于整体升级。以后有实质收益的新版本时，应评估上游修复、平台兼容性和本地定制的维护成本，再更新固定提交；不自动追踪 master，也不永久冻结。若需要框架补丁，应保留小而明确的改动、来源和对应验证，争取上游接纳；升级时能判断补丁是否删除或重新适配。
- 自动化的元数据/面板通知可主要留在 host；实时参数同步仍可能涉及 App 共用的队列与调度，风险不能说成零。宿主时钟会触及共用的键盘演奏状态机，属于行为变化较集中的部分。完整效果器程序参数应只适配现有卡带+档位，不改变效果算法、切换包络及 App 操作语义。DRY 总线应只适配既有四路输出，不重写 DSP、不改 App 的设备协商。
- 长期兼容契约不仅有参数 ID，还包括范围、枚举及归一化映射。39 档完整程序参数如果以后扩展，不能直接扩大范围而让旧工程中的归一化自动化值指向别的程序；程序选择是否自动化仍待决策。

#### 固定提交解决什么、不解决什么

`.gitmodules` 指向官方仓库，父仓库的 gitlink 固定准确提交，没有随主分支自动漂移。CI 递归检出同一提交；VST3 SDK 独立固定为 `v3.8.1_build_84`。这有利于复现、回退和稳定，不等于“过时”或“以后不能升级”。`IPLUG2_DIR` 可覆盖本地依赖路径，发布构建需要确认用的实际路径和提交。

依赖更新的主要成本在已有集成：独立 App 使用 `iPlug_app_override.cpp` 和 `iPlug_app_host_override.cpp` 替代上游 APP 实现，后者包含大量设备、MIDI、状态保存定制；Windows 的宿主源文件选择与平台入口也与所锁定框架相关。未来升级必须检查新头文件、生命周期、构建脚本和本地覆盖文件之间的语义兼容，不能仅以“编译通过”判断没有回归。现有源文件选择门禁防止误用／重复编译原版，不检查全部上游差异；已删除的 `tools/check_host_override_drift.py` 不能当作仍在运行的保障。

| 路径 | 短期收益与成本 | 中期收益与风险 | 当前建议 |
|---|---|---|---|
| 继续锁定当前提交 | 保持已验收的 App／插件基线，避免无收益迁移；不会自动补全参数点／斜坡 | 以后仍需关注平台兼容和上游修复，长期完全不维护会积累差异 | 当前合理，配合有目的的上游跟踪；不是永久冻结 |
| 因具体需求增加小范围框架适配／补丁 | 能针对明确瓶颈交付，但要承担实时／跨格式检查 | 每次升级要判断补丁能否删除或重新适配；尽量争取上游接纳 | 只有创作需求和精度目标确立后再采用，不先补再找用途 |
| 未来整体升级到有明确收益的新提交 | 可取得上游缺陷修复、系统／编译器兼容或需要的功能；初期回归面较广 | 减少长期积累的旧接口和本地补丁，但要维护覆盖实现兼容 | 单独 PR，写清具体收益、迁移差异和 App／插件回归范围 |
| 自动追最新 master、或直接采用旧实验分支 | 当前没有已证明的任务收益，会引入额外变量 | 发布难复现，分支未合并能力的维护责任落在项目自己 | 不建议作为默认策略 |

适合的长期方式是“**固定已验收基线 + 有理由的升级 + 小而可追踪的必要补丁**”。以后出现上游修复或系统兼容需求时，再比较收益和回归成本；不因为当前不需要升级就决定永不升级，也不为了第二阶段而把框架迁移捆绑进同一批代码。

来源：[iPlug2 官方仓库](https://github.com/iPlug2/iPlug2)、[锁定提交](https://github.com/iPlug2/iPlug2/commit/d54f69050f517e43b941d88c2a170f0a840b9ee4)、[本地构建配置](../host/CMakeLists.txt)。上游状态是核查日事实；本节没有宣称当前基线永远是最新版本。

### 9.3 宿主自动化的机制、用途与必要性（问题 2）

通俗地说，**让 DAW 不只记住你弹了哪些音，还记住“什么时候把哪个旋钮转到哪里”，以后按时间线重放，并允许修改这条变化曲线。**

例如 8 小节的声音从闷到亮、最后两小节加大混响、结尾收低内部 MASTER：可以边听边操作面板录下曲线，也可以直接在 DAW 里画滤波／BLEND／MASTER 的变化。之后移动曲线节点，不必重新表演整段。保存工程可以同时留下音色快照和随时间变化的参数数据。

机制包括稳定的宿主参数编号、范围／曲线、面板操作的开始／变化／结束通知，以及 DAW 回放到实时引擎和面板显示的反向同步。它与几个相近概念不同：

| 概念 | 记录／控制的是什么 | 当前状态与关系 |
|---|---|---|
| 工程音色保存 | 当前机器配置的快照 | 第一阶段已有；不保存过去的全部旋钮动作 |
| MIDI 音符 | 音高、按下／松开时机和相关表情 | 第一阶段已有输入路径，DAW 可以录制回放 |
| 插件内部 MIDI Learn | 把进入插件的 CC／音符等映射到控制动作 | 已有；可利用 DAW MIDI 片段记录，但依赖映射、初始状态和消息实际进入轨道 |
| 宿主参数自动化 | DAW 时间线上直接表示插件参数值 | 尚未实现；DAW 可显示名称、曲线并进行参数映射 |
| 轨道音量／声像／外接效果器自动化 | DAW 自己或后接设备的参数 | 现在就能使用；不能替代全部 Lunar 内部变化 |
| 实时录音频 | 当时实际发出的声音 | 第一阶段输出具备；能保留所有可听操作，但不能独立编辑每次内部动作 |

若核心用途是即兴、声音探索和录音频，自动化可以推迟；若经常反复编排、修改音色运动、让控制器操作成为可编辑的时间线数据，则收益很大。它不是插件发声／录音的必要条件，但在成熟通用合成器中是常见能力，不能简单归为小众高级功能。

“做自动化”也不等于“195 或 201 个参数全部开放、所有程序切换都可录、完整采样级曲线一次做完”。范围和精度可以分别选择；已发布参数则必须正确同步并保持兼容。保留较小但可靠的宿主接口，是可长期成立的产品范围，不必当成待消除的临时状态。

来源：[Ableton 参数配置与自动化](https://www.ableton.com/en/live-manual/12/using-plug-ins/#plug-in-configure-mode)。MIDI 消息记录与宿主参数自动化是不同路径，参见 [u-he 官方说明](https://u-he.com/support/faq/troubleshooting/)；其中消息类型仍以实际 MIDI 协议为准，弯音／压力不能统统等同于 CC。

### 9.4 自动化：实际范围与编号

从 `build_panel_layout()` 排除菜单后，旋钮、按钮、拨杆和摇杆共对应 **195 个不同参数**：116 个旋钮、61 个按钮、16 个拨杆、摇杆 X/Y 两轴。模块分布：经典 DRONE 80；DRONE 3/6 共 24；VCO A/B 共 16；VCF 11；包络 A/B 共 12；LFO A/B 共 6；摇杆及偏移 4；PREAMP 1；包络跟随器 2；五步音序器 12；混音器 20；效果器 7。

- `sequencer.clock` 和 `effector.phone` 没有对应面板控件；不能因为它们在注册表里就对外开放。键盘菜单、效果器程序内部参数继续按原计划排除。
- DRONE VOICES 六键、总 MUTE、四个光敏头是独立动作/状态，不是上述参数。触摸键盘、接线、REC、RESET PANEL 也不能按普通旋钮机械注册。
- 注册表有 349 个参数，最大数字 ID 为 415，编号不连续。iPlug2 的 VST3 `IPlugVST3ControllerBase::Initialize` 和 AU `kAudioUnitProperty_ParameterList` 都把连续的参数索引直接当宿主 ID。`kFlagCannotAutomate` 不是隐藏参数功能。
- **建议修订原来的“宿主 ID = 内部 ID”**：在 spec 中显式定义永久不变的连续 `host_id`，生成它与内部 ID 的双向映射。发布后只追加，不因面板布局、模块顺序或名称改变而重排；不改变现有机器存档 ID。第一阶段宿主参数为零，因此现在可以定这份契约。若坚持两套 ID 数字相同，就需维护 AU/VST3 的稀疏 ID 适配；不建议用几百个空参数占位。
- 参数名带模块前缀；枚举用真实档位文字，不按屏幕上下位置推测编号。归一化值与现有 `knob_to_value` / `value_to_knob` 一致，保留原有 DSP 平滑，不统一重调音色。

#### 讨论过的范围选项（全部待决策）

- **195 个现有面板参数**：只按已盘点清单开放，不自动加入其它动作。
- **195 + DRONE 六键 = 201 个宿主控制项**：此前推荐的候选方案，因为 DRONE 的开关也有编排价值；六键需要单独定义状态、保存和同步，不能假装已在参数注册表里。
- **再加入总 MUTE／四个光敏头**：需要决定临时演奏动作如何映射和恢复；这与 App 的“MUTE 不保存、光敏手势不保存”语义有关，不能未经决定就改变。
- **只先开放实际需要的常用参数**：属于后续用途讨论允许的较小范围；尚未定清单和数量，不能把 201 当作最低合格线。

编号建议是永久连续 `host_id` 与稀疏内部 ID 的映射，而不是重排已有机器存档 ID。宿主参数发布以后，兼容契约不仅包括 ID，还包括范围、档位、单位和归一化曲线；未来 UI 布局改变也不能让旧工程的曲线控制到另一个参数。

盘点依据：[panel_ui_layout.h](../host/include/host/panel_ui_layout.h)、[参数 spec](../spec/machine/lunar24.json)、[generate_registry.py](../tools/generate_registry.py)。195 项的抽样分发检查只说明事件能到引擎，不证明每个参数都适合作为宿主自动化产品接口。

### 9.5 自动化实时桥接：六项有条件的正确性要求

1. `postParameter()` 会修改 UI 拥有的保存状态，并写入单生产者队列；不能从任意 `OnParamChange()` 回调调用。iPlug2 明确说该回调可能来自音频线程，`kHost` 只说明来源，不足以证明线程身份。应分清 UI 手势、宿主处理期事件、非处理期参数更新，再交给有明确所有权的桥接层。
2. `parameterFromAudioThread()` 没有 sample offset，把参数事件排在当前块起点；不能直接用作带时间位置的自动化接口。运行时已有绝对采样时间的 `EventTimebase`，可扩展宿主入口复用它。
3. `EventTimebase` 连续事件容量为 64；满时仅能合并同参数事件，新的不同参数可能被拒绝。`sendParameterFromAudioThread_()` 没有检查运行时入队结果，随后仍可能回写保存值。195 个参数批量初始化不能直接逐个塞入该队列。需设计有界的事件交付/分段处理和容量策略，保证状态与实际声音一致，保留音符事件的容量保障。
4. 音频到 UI 的 `fromAudioQueue_` 只有 256 项，同时承载 MIDI 变化、动作、旧接线计划的回收。密集自动化不能每个采样点都往里面追加记录；建议连续参数采用带版本/来源的最新值同步，动作与资源回收继续有序处理。保存工程时取得最新一致状态，不能只等下次 `OnIdle`，也不能在保存回调中无条件并发消费 UI 队列。
5. 新增 iPlug 参数后，整机恢复、RESET PANEL、MIDI Learn、面板和 DAW 自动化必须同步同一份有效值。VST3 还持有控制器参数副本，恢复机器状态后要同步它。初始化/恢复不是用户手势，不能把所有参数变成一次 `performEdit`，更不能用参数默认值覆盖刚读入的第一阶段工程。切换前排队的旧自动化也不能覆盖新机器。
6. 自绘 `IControl` 没有绑定宿主参数。拖动、滚轮、双击复位、按钮/拨杆、摇杆两轴均须接入手势开始/变化/结束；关窗、丢失焦点时也要收尾。宿主回放仅更新显示和声音，不回报成一次新的手动编辑。MIDI 改值还要与接管/相对旋钮的基准同步。

**MIDI 录制待选**：推荐本轮面板操作可录宿主自动化，插件内部 Learn 继续控制声音并同步参数值，但不自动额外写一条宿主自动化；控制器数据仍可作为 DAW 的 MIDI 片段回放，或用 DAW 自身参数映射录自动化。若希望插件 Learn 也直接录宿主自动化，需补非音频线程的宿主通知、无实体鼠标的手势结束规则，并避免 MIDI 回放又被写成自动化。无论选哪种，宿主曲线回放都不能反向制造新的编辑手势。

#### 六项要求对成熟引擎的影响范围（问题 3）

这里的“核心”需要拆成两层：一层是振荡器、滤波器、包络、效果器等**声音算法**，另一层是决定“何时、由谁、把哪个值送进去”的**控制／调度／状态路径**。不改声音算法不等于声音绝不会受影响；控制顺序、丢事件或恢复时机出错同样会改变听到的声音。

| 六项要求 | 主要修改面 | 对 App／声音的潜在影响 | 相对风险与约束 |
|---|---|---|---|
| 1. 区分回调线程和来源 | 插件参数桥接、共用引擎入口、队列所有权 | 多生产者误用单生产者队列可引起状态竞争；不能从宿主回调直接修改 UI canonical state | 中高；先明确所有权，不增加音频线程锁／分配 |
| 2. 保留参数时间位置 | 宿主事件入口、采样时间调度 | 改变参数何时生效；应保留 App 既有输入行为和 DSP 平滑 | 中；不统一重调算法或平滑常数 |
| 3. 容量与事件交付 | EventTimebase、批量初始化、分段／快照策略 | 丢参数会导致保存值、界面与声音不同，也可能挤占音符容量 | 中高；容量有界，拒绝／合并规则明确，保证音符关键事件 |
| 4. 音频到 UI 同步与保存 | 共用 fromAudioQueue、最新值快照、OnIdle／SerializeState 协调 | 队列还承担旧接线计划回收，不能只为自动化丢弃其它消息；影响 App 的 MIDI 和接线 | 中高；连续值与动作／资源回收分开处理，保存获得一致状态 |
| 5. 恢复、默认值、MIDI、面板一致 | 插件 IParam／VST3 控制器缓存、机器状态切换 | 老工程被默认值或旧事件覆盖会直接改变音色；重放反写宿主会产生循环 | 中高；初始化／恢复不算手动编辑，保留旧工程 |
| 6. 控件手势 | 共用 panel_editor 自绘控件和插件通知桥 | App 的鼠标／滚轮／双击／摇杆操作可能回归，丢焦点可能留下未结束手势 | 低至中；通知主要限于插件，原有控件声音和手感不变 |

这些是按改动性质判断的相对风险，不是已经测得的故障概率。目标是让新增宿主输入正确进入既有声音系统；无需为了自动化重写振荡器、滤波器、效果算法。不过第 1–5 项触及共享实时路径时，必须回归独立 App 的 MIDI、状态、接线和演奏。

MIDI Learn 是否同时写宿主自动化是独立产品选择。先前候选建议是不自动额外写一条：控制器仍可录为 MIDI，或在 DAW 里映射成参数自动化；这能避免回放 MIDI 又被误当作新手势。若需要直接录，也可以做，但要设计线程切换、手势结束和来源区分，不是简单多调一次宿主通知。

### 9.6 包装层的自动化精度限制

- 2026-10-08 补查版本机制：官方远端默认分支 `master` 的 HEAD 与项目锁定提交同为 `d54f69050f517e43b941d88c2a170f0a840b9ee4`。以下是本次核查时上游默认分支的实现边界，不能归因为项目落后于上游，也没有“升级到当前 master 就解决”的路径。上游另有 2021 年的 `VST3/paramqueue` 分支，不等同于较新的稳定升级目标。
- 锁定 iPlug2 的 `IPlugVST3ProcessorBase::ProcessParameterChanges()` 只读取每个参数队列的最后一点，虽然把该点的 offset 交给回调，其余点已经丢失。
- AU 的 `DoScheduleParameters()` 只处理 immediate 事件，没有处理 ramp 事件。不能仅在 Lunar 插件中实现 `OnParamChange` 就宣称两种格式都完整支持块内曲线。
- **完整精度目标的候选方案，尚未决定采用**：补小范围、可追踪的插件包装层适配，接收宿主实际提供的时间点/斜坡，再送到有界的实时桥接层；保留现有 DSP 平滑。用同一曲线在不同块大小下比较结果，并在 macOS/Windows 原生构建中检查包装层入口。validator / auval 通过不能代替这项检查。另一种较小范围的选择是先交付受上述限制的自动化，但必须明确精度边界。自动化本身及其精度目标均应先按创作需求决定，不因技术上能补而自动扩大本轮范围。

#### 自动化能力与自动化精度要分开决定

以 48 kHz、512 样本块为例，一块约 10.7 ms。块内只保留一个控制点／不支持完整斜坡意味着控制轨迹存在这个量级的处理窗口和重建边界，**不是音频会每 10.7 ms 中断一次**。对慢速扫滤波与快速、密集、节奏性的变化，实际影响可能不同；不能未经同宿主听音／渲染比较就断言现有精度足够或完全不可用。

候选取舍：

- 暂不做自动化：没有理由只为尚未采用的功能修改框架。
- 先交付范围受限、精度边界明确的自动化：改动较少，但需要验证预期创作方式，不能宣传完整块内曲线能力。
- 明确需要完整点／斜坡后补小范围包装层：跨 AU／VST3 处理点和斜坡、接到有界实时调度，成本和风险更高；仍须保留原 DSP 平滑，不能以逐点输入代替声音层的平滑策略。

完整点／斜坡接收、插件内事件时机正确和可听的自动化质量是相关但不同的验证目标；宿主本身也决定实际发送哪些点。validator／auval 通过不能替代这些验证。

因此之前“需要补包装层”的建议已经调整为**满足完整精度目标时的候选方案**，不是本轮必须项；当时也没有“整体升级到最新 master 就解决”的路径。依赖维护按 9.2 独立评估，不能只围绕这一处问题作长期决定。

### 9.7 效果器切换的特殊含义

`ToggleControl` 的 1–2–3 操作先调用 `loadSlotCartridge()`，再改变选择参数；卡槽选择 `slotCartridge_` 是 UI 暂存值，工程保存的是左右实际加载的卡带。因此仅录制 0/1/2 不能完整复现换卡带操作。音频回写中的 `syncParametersFromAudioThread()` 还会为这两个参数触发卡带加载，不能不区分来源地复用。

**待选**：推荐 DAW 对外是左右各一个 39 档的“卡带 + 程序”参数，替代两个仅 3 档的宿主参数，面板保持原样；操作加载拨杆时记录实际完整程序。只切换候选卡槽不改变声音，也不产生程序自动化。替代方案是只自动化各侧当前已加载卡带内的 1–2–3，明确不录制换卡带；或本轮暂不开放程序选择。

#### 为什么不能只把面板的 1／2／3 暴露给 DAW

例如左侧当前是卡带 A 的程序 2，后来面板选择卡带 B 并拨到程序 2。如果宿主只记数字“2”，便不能知道这次应使用 A 还是 B。卡槽里挑选候选卡带、实际加载到左／右效果器、该侧选择哪个程序，是相关但不同的状态。

当前一个完整效果程序已经由 13 张卡带 × 3 个程序构成；对宿主提供 39 档，是给现有能力一个完整地址，并不要求增加新的效果算法或把 App 面板改成 39 档大旋钮。`DualEffector` 原本就组合 cartridge 与 select，代码需要桥接的是宿主表达和现有内部状态。

| 选项 | 收益 | 限制与长期代价 |
|---|---|---|
| 左右各一个完整 39 档参数 | 可明确重演该侧使用哪张卡带的哪个程序，不依赖 UI 临时候选槽 | 必须一致更新卡带和档位，冻结已发布程序身份与归一化映射，验证切换时序 |
| 仅自动化当前已加载卡带内的 1／2／3 | 开放范围较小，可用于固定卡带的工程 | 不包含换卡带过程；相同档位取决于已加载卡带，不能声称完整记录程序切换 |
| 暂不自动化程序，只开放 X／Y／Z、BLEND、MASTER 等需要的控制 | 避开程序切换的复合状态，保留常用渐变能力 | 切程序只能现场操作／录音频，或以后另加明确参数；这是可持续范围，不必视为权宜之计 |

#### 对独立 App 的风险边界（问题 5）

目标应是保持 App 现有“选候选卡带 → 拨杆加载并选程序”的操作、左右独立效果、控制平滑和约 15 ms 淡出／重置／淡入行为。宿主完整程序参数只是适配；它不意味着需要改算法、保留旧尾音或改变已经按听感打磨的音色。

真正风险在于复合状态不一致、宿主／UI 相互回写以及来自 `syncParametersFromAudioThread()` 的额外加载动作。如果先应用新卡带再延后应用档位，中间可能短暂选中错误程序或多触发一次切换；需要把逻辑上的一次程序变化一致交付，区分来源，并验证 App 原路径保持不变。

中期兼容尤其重要：若以后从 39 档增加到 42 档，不能直接扩大范围，让旧工程的归一化自动化值映射到另一个程序。稳定 ID、离散值和归一化解释应在首次发布前设计好。**“为了这次实现方便”既不应迫使改 App，也不应留下未来无法解释旧曲线的接口。**

### 9.8 DAW 时钟与走带

现有 `ControlEventKind::clock` 仅驱动键盘琶音器和 16 步音序器，四分音符内有 4 步（十六分音符），SINGLE/TWIN/SPLIT 共用节拍。它不会自动同步五步音序器、LFO、DRONE 内部振荡或效果延迟；这些继续按原速度运行，扩展同步需要另列范围。

需要补足的行为：
- 显式的宿主时钟归属：不能等第一拍到来才停内部时钟，也不能让修改菜单 BPM 或 CLOCK 插孔又抢回控制。HOST 模式忽略 MIDI 时钟；插件的 CLOCK/RESET 插孔在该模式下如何处理要写明，建议均由宿主负责。独立 App 保留现有行为。
- 从 PPQ（以四分音符为单位的播放位置）计算块内时钟位置，处理块边界、浮点舍入、变速、循环、跳转、负位置/预滚和离线渲染，不能用 UI 定时器或墙上时间驱动。框架时间信息存在默认/无效值，AU/VST3 包装层还未完整保留有效性；不得把缺失信息静默当成有效的 120 BPM。
- 现有 `externalClockPulse_()` 用相邻脉冲间隔推算关门时间；第一拍没有完整间隔，暂停后也可能读到跨暂停的旧间隔。宿主模式应明确生成开/关门或提供周期，停止时释放琶音/音序产生的音，清理过期事件及相位历史。
- 不能用整机重建处理播放/停止；也不能直接借 `ControlEventKind::sync` 保持和弦：它经过 `releaseRun_()` 调用 `reset()`，会清掉和弦。已有 `restartPattern()` 能保留和弦，但本身不负责关门或按样本定位，需要组合成明确的走带接口。
- 当前插件 `OnReset` 会请求全体键盘 gates reset。宿主走带变化、DAW 主动 Reset、旁路及采样率重建应区分，避免停止策略和既有复位路径互相覆盖。

**待选的产品规则**：
1. 保持原设想“插件始终跟 DAW”；或增加每实例 HOST / INTERNAL。推荐后者：新实例默认 HOST，第一阶段旧工程没有新设置时用 INTERNAL 兼容旧行为；设置写入插件可选分段，不写 App 全局文件。若坚持始终 HOST，应接受旧工程的琶音/音序行为随升级改变。
2. 推荐 HOST 下播放、跳转、循环回绕时，从下一处十六分网格开始第 1 步；停止则停止自动步进并关掉生成音，DRONE 和效果尾音不全局静音，普通 MIDI 演奏仍可使用（宿主自身 note-off / Reset 照常处理）。这保证节拍对齐，不等同于从任意 PPQ 恢复整段乐句的对应步骤；后者涉及长度、方向、随机步、RHYTHM 和当前和弦，需另做定位逻辑。

#### 修改面与行为风险（问题 6）

这是后续功能里最集中改变演奏行为的一项。工作主要落在 `host/plugin.cpp` 的宿主时间读取／事件桥、iPlug2 的 AU／VST3 时间有效性传递，以及共用的键盘时钟、`ArpSeq` 演奏状态机；不是重写振荡器或效果算法，但错误会直接表现为起拍不齐、重复／漏步、停止挂音或和弦丢失。

| 补齐项 | 影响面 | 需要保护的行为 |
|---|---|---|
| HOST／INTERNAL 时钟归属 | 插件实例设置、共用键盘时钟模式 | App 继续沿用内部／MIDI／插孔接管规则；HOST 下不能被内部 BPM 或插孔意外抢回 |
| PPQ 到块内事件 | 插件时间桥、框架有效性、运行时事件时间 | 实时与离线按音频时间推进，处理首拍、块边界、变速、负位置和预滚 |
| 开／关门与停止 | 共用键盘 gates、外部时钟相位历史 | 停止内部生成音，不全局关闭 DRONE／效果尾音，普通演奏仍能使用 |
| 保和弦重启 | ArpSeq restart／reset 路径 | 重启位置不意外清空 held chord，不直接拿会 releaseRun 的 sync 代替 |
| 循环、跳转、继续 | 插件走带检测与键盘序列位置 | 明确是重新从第 1 步，还是追赶整段乐句的正确位置；不暗中混用 |
| 宿主 Reset、旁路、采样率重建 | 插件生命周期与已有 notesOffRequested | 区分真正重建与走带通知，避免新的停止策略被原复位路径覆盖 |

两种位置策略的差别必须讲清楚：

- **节拍对齐后从第 1 步开始**：从下一处十六分网格重新开始序列；实现范围相对明确。
- **绝对乐句位置追赶**：跳到第 17 小节时计算“如果从开头一直播放，现在应处于哪个音／哪一步”；涉及步长、方向、随机、RHYTHM、和弦历史等，不能由读取 BPM 自动获得。

前者是此前推荐的候选，不是业主已确认的规则。拍号变化是否改变重启／小节对齐，也要随所选规则明确，不能只写“同步 DAW”而让实现自行猜测。

旧工程兼容建议：新增每实例 HOST／INTERNAL，若采用，新实例可默认 HOST，第一阶段工程缺少新字段时回到兼容旧行为的 INTERNAL；这里的 INTERNAL 应保留旧有 MIDI／CLOCK 接管能力，不是把所有外部输入都禁掉。设置放插件 chunk 的可选分段，不改 App 全局文件。仅实现这一隔离也需要验证 shared core 没有被默认模式改变。

如果业主主要录自由演奏，整项可以延期；若想要严格跟鼓点的内部序列，它会成为相应工作流的关键能力。普通 DAW MIDI 音符的时机已经由宿主提供，不需要先完成这一项。

### 9.9 DRY 辅助输出

- 现有 DRY A/B 是 **VCO A/B + SUB、经过各自 VCA 后** 的信号，在混音器、滤波器、失真、效果器和 MASTER 之前。它们不是六个 DRONE 的分轨，也不是完整混音的干声。沿用现有电平与总 MUTE/切换淡出语义。
- 建议沿用原计划：WET 一个立体声主总线，DRY 一个立体声辅助总线（左 A、右 B）。iPlug2 用 `0-2.2` 表示两组立体声总线；`0-4` 是一组四声道，VST3 默认映射甚至是 Ambisonics，不能混用。须兼容宿主仅使用 WET 的配置。
- iPlug2 的 VST3 `ProcessAudio()` 会按块更新连接；AU 渲染路径也会更新总线连接，而且含有按每总线 2 声道计算的代码。因此不应假定开关辅助输出必定先调用 `OnReset`。推荐引擎固定 0 入/4 出，只把已启用输出接到宿主，其余使用预分配缓冲，不因总线开关重建机器。
- 当前 `ProcessBlock` 的“连接数不足就全静音”和按 `NOutChansConnected()` 遍历的写法要改为检查具体通道/总线。框架明确说明总连接数假定通道连续；只有 DRY 启用时，这个假定不成立。
- 校验 AU 各总线拉取次序/次数，确保一次时间片只推进一次引擎；VST3 覆盖辅助总线不活跃、零通道、缺失缓冲、主输出未连接，以及 32/64 位宿主缓冲。真正的 DRY A、B 两个单声道总线是另一种拓扑，需要额外处理 AU 的立体声假设，暂不建议扩大到它。

#### 为什么建议调整“开关输出就重建”的旧策略（问题 7）

引擎的 `RuntimeOutput` 和 `DeviceAdapter` 本来就生成 WET L/R、DRY A/B；第一阶段只是向 DAW 交付前两路。第二阶段的主要工作是把已有结果接到宿主总线，不是新增两台振荡器、复制一套 DSP，也不意味着音色或计算量必然翻倍。

“插件引擎固定 0 入／4 出”指插件内部输出容量和适配器准备方式稳定。DAW 只要 WET 时，另外两路写入预先分配的缓冲；启用 DRY 时改接到对应宿主缓冲。不因为总线启用状态变化就销毁重建整台机器，能避免尾音、相位、演奏状态重启。**独立 App 的物理声卡能力协商、2／4 输出选择不需要跟着改。**

保留既有 DRY 电平映射、总 MUTE 和状态切换淡出；不要为了总线方便重调它们。DRY A/B 只含各自 VCO + SUB，经 VCA 后取出，在混音器／滤波／失真／效果／MASTER 之前；不是六路 DRONE stems，也不是把 WET 关混响后的全机干声。

| 工作 | 修改面 | 主要风险 |
|---|---|---|
| 声明 WET 主总线 + DRY 辅助总线 | 插件 config、AU／VST3 格式适配 | 把两组立体声误写成单组四声道；旧工程主输出拓扑兼容 |
| 连接与预分配缓冲 | ProcessBlock、通道连接检查、32／64 位包装路径 | 空／缺失缓冲写入、只启用辅助输出时错误静音、假设连接连续 |
| AU 多总线拉取 | AU 包装层、时间片推进判断 | 同一时间片被渲染两次，导致速度／声音错误；不能只在 VST3 上验证 |
| 保持运行时与 App 行为 | 插件准备策略及必要的适配层 | 总线切换意外重建机器；共用适配器修改影响 App 设备切换 |

因此这项是**中等范围的宿主集成变化，而不是核心声音算法重写；也绝不是只把声道数从 2 改成 4 就完成**。若现阶段不需要把 VCO A/B 分开做外部效果／混音，立体声 WET 已足够，可以延期整个功能。

### 9.10 第三阶段：外部音频输入的用途与待核查范围

当前插件声明 0 输入，第三阶段的价值是让 DAW 里其它轨道或外部来源的音频进入 Lunar 的 PREAMP／内部处理路径。这能扩展声音设计和处理器用途，但不是合成器正常演奏、录 MIDI、录立体声音频的前提。

原方案考虑 AU music effect／VST3 侧链，初估 1–3 个 PR。它尚未经过与第二阶段同等深度的格式、宿主和状态兼容核查，不能直接当成已定架构或确定交付量。真正启动前要明确：外部音频喂给哪些输入、单／双声道如何解释、是否同时保留 MIDI 演奏、宿主如何路由、无输入时如何处理，以及是否影响现有乐器身份与旧工程载入。若需要新增独立格式身份或产品形态，要先评估兼容，不能悄悄替换已有插件。

如果保留既有 core 处理路径，主要改动有望集中在宿主输入总线和适配；但目前不足以保证风险很低。独立 App 的输入设备选择和既有 PREAMP 行为应继续保留，新增插件输入必须独立验收。

**AUv3 和 CLAP 已决定不做，本次没有重新打开这个决定。** 第三阶段当前只保留外部音频输入作为按需评估的方向；没有施工安排。

### 9.11 保护成熟独立 App：整体修改面与风险边界

业主的首要约束是：不要为了完成插件阶段任务，破坏多轮打磨的独立 App，也不要以短期接线方便换取中期难维护的架构。

| 领域 | 是否需要重写声音算法 | 可能影响 App 的地方 | 风险判断与隔离目标 |
|---|---|---|---|
| 宿主参数定义与通知 | 不需要 | 共用面板控件、通知桥 | 较低至中；插件通知不改变 App 操作语义 |
| 自动化实时交付、保存一致性 | 不需要，但可能触及共享控制／调度 | MIDI、接线资源回收、状态保存／切换 | 中高；六项所有权和容量要求不能跳过 |
| 完整效果程序参数 | 不需要 | 共用卡带／档位动作及其回写 | 中；保持现有切换包络和 App 面板，防止组合状态短暂错误 |
| DAW 同步 | 不需要重写振荡器／效果；会改演奏状态机 | 共用 keyboard clock、ARP／SEQ、gates、reset | 行为风险较集中；显式模式，旧工程和 App 保持旧语义 |
| DRY 多输出 | 不需要，已有四路信号 | 若调整共用适配器，可能影响设备输出 | 中；插件总线独立适配，App 声卡计划保持原样 |
| 整体 iPlug2 升级 | 不直接改变 core DSP | 本地 APP overrides、平台构建、窗口、音频／MIDI 生命周期 | 回归面较广，成本取决于具体上游差异；单独评估 |
| 第三阶段音频输入 | 原有输入 DSP 可复用，但尚未充分核查 | 共用输入适配与路由 | 待核查，不先承诺低风险 |

core 继续保持 framework-free，音频线程不分配、不等待、不加锁。host 与 core 的目录边界不是自动的风险隔离：共享队列、控制时机、保存规则即使只改在 host 也能影响实际声音。最终以具体 diff、针对性验证和 App 听音回归判断，不能仅以“没有改振荡器文件”宣布零风险。

后续如实施，每个 PR 只做已决定的能力，必要的共用引擎改动单独审查；继续提供 App 下载包，对受影响 MIDI、接线、时钟、输出和存档路径做对应回归。参数 ID／范围／归一化、插件身份、旧工程缺字段行为属于长期契约，需在第一次发布相应能力前定清楚。

### 9.13 条件式实施拆分与验收建议（只有决策后才排期）

若采用较完整的第二阶段范围，预计 **7–9 个小 PR**，取决于自动化精度与走带选项；这是当前核查后的估计，不是交付承诺。先确认本节产品规则，再改代码。

| 顺序 | 交付 | 必要验证 |
|---|---|---|
| 1 | 参数清单、固定宿主 ID、映射和曲线 | 明确的历史 ID 对照；增删/重排不能改已有编号；枚举与归一化往返 |
| 2 | 参数桥接、实时事件/最新值同步、工程恢复 | 密集多参数、队列压力、保存前尚未 Idle、未准备/暂停处理、恢复后默认值不覆盖音色；音频路径无分配 |
| 3 | 自绘控件手势、选定的 DRONE/效果器/MIDI 策略 | 各输入方式录制/回放、关窗收尾、宿主回放不回报成手动操作；App 回归 |
| 4 | AU/VST3 时间点/斜坡适配（若采用） | 同块多个点与斜坡、跨块及长块、不同块大小、原生入口检查；保持 DSP 平滑 |
| 5–6 | 宿主时钟、走带与兼容选项 | 首拍、停止、续播/跳转/循环、变速、拍号、预滚、离线导出、SINGLE/TWIN/SPLIT、无效时间信息及旧工程 |
| 7 | WET + DRY 输出总线 | DRY 与引擎既有四路结果一致、只 WET/只 DRY/同时启用、切换不断尾音、不双重推进、旧工程主轨不变 |
| 8–9 | 两种格式集成验收与必要修正 | Mac Ableton 自动化与走带、多实例、保存重开、离线导出；Windows 构建/validator；App 原有 MIDI、时钟、输出和状态回归 |

仍待业主决定：额外自动化控件；效果器完整程序或仅档位；是否录制插件内部 MIDI Learn 操作为宿主自动化；自动化精度范围；HOST/INTERNAL 与跳转规则。编号映射、队列所有权和缓冲策略属于实施方案，确认后再修订 9.1 的原始设想；目前不按旧设想直接实施。

这份拆分不是要求按表启动 7–9 个 PR；冻结全部后续功能时，只保留第一阶段基础维护。只选择部分能力时应删去无关实施项并重新估计。第三阶段音频输入不包含在这份第二阶段拆分里。以上风险判断、推荐项和估计均不能代替业主之后的产品决策。
