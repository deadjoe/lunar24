## 2. Clause-1 — norm→DSP mapping (named, PROVISIONAL)

```
depth = modNorm * kModDepthFromNorm     (linear)
kModDepthFromNorm = 1.0
```

- Both the registry unit and the setter are **norm 0..1** (`double`), so this is a
  registry-agreeing unit; no invented scale. Marked `PROVISIONAL` in the header comment — the
  norm→depth model is a software model (no manual/DSP circuit evidence), same class as the pulser
  model already flagged earlier. Declared once:
  `core/include/lunar24/core/machine_runtime.h` `static constexpr double kModDepthFromNorm = 1.0`.

## 3. Clause-2 — default value, OLD vs NEW

**OLD (pre-D1):** `mod` was UNCONSUMED. Independent of the knob, `tick()` always fed the audio
oscillator a raw `±1` LF square → effective modulation depth **1.0**, whatever the panel held.

**NEW (D1):** `tick()` feeds `lf.square() * mod_`, with `mod_` defaulting to **0.5** — the
registered `drone_3/6.mod` default. Effective modulation depth default is now **0.5**.

Behavioral difference, stated precisely:

| state                                  | OLD effective depth | NEW effective depth |
|----------------------------------------|---------------------|---------------------|
| FM **and** AM both off (product default) | 1.0 (irrelevant)   | 0.5 (irrelevant)   |
| FM **or** AM engaged by the user       | 1.0                 | `modNorm` (default 0.5) |

The two rows are distinct because `mod` is **inert when FM and AM are both OFF**:
- FM off → `setFmDevHz(0.0)` → `instRate` independent of `mod_`.
- AM off → `setAmDepth(0.0)` → `am = 1.0 + 0.0*mod_ = 1.0`, independent of `mod_`.

So the **default drone sound (FM/AM off) is bit-identical before/after** — the wiring cannot be heard
in the shipped default. The audibly-visible change is the modulation-depth magnitude **when FM or AM
is engaged**: OLD fixed 1.0 → NEW = knob (default 0.5).

⚠️ **FLAG to @Kimi (default-behavior consequence):** wiring the knob makes drone_3/6 FM/AM depth
depend on `mod` (default 0.5). That halves the pre-wire FM/AM depth (was 1.0). This is the faithful
consequence of honoring the registered 0.5 default (I did **not** change the registry default — it
stays 0.5 — only the DSP consumption). If the intent was to keep the pre-wire FM/AM magnitude while
merely making the knob functional, the registered default would need to be 1.0; surface to
@Kimi/owner for a ruling, not decided here.

## 4. Clause-3 — existing tests that pin the OLD default behavior

**Finding: NONE pin the OLD default `mod` sound.** Because `mod` is inaudible in the default
(FM/AM off) and no test that exercises the drone3/6 channel asserts an absolute modulation depth.
Enumeration that could have pinned it, and why each stays green:

| test | touches drone mod? | why green |
|------|--------------------|-----------|
| `test_machine_runtime` ⑪ drone combo (fm/am switches) | channel, via switches | asserts the 4 combos **differ from each other**, never an absolute depth; robust to 1.0→0.5 |
| `test_machine_runtime` ⑫ tone-gate | channel | pitch=0 + noise; `mod` not wired-in → not exercised |
| `gh19_alias_probe` drone3/6 cases | channel | sets `fm=am=0` → `mod` inert → output unchanged (no ripple); sees only the fm/am off path |
| `test_drone_mod.cpp` (P3-②) | the osc primitives | tests standalone `FmAmVoice(seed, sr, fDev, depth)` with **explicit ctor args**; does not route through the SynthRuntime `setMod`/tick path, is insulated from the default |

No test reads `modApplied()` (the getter is new in D1). So clause-3 answers: **no re-pin needed**; the
20-line behavior difference is in the FM/AM-engaged state, which no legacy test asserts absolutely.

## 5. Clause-4 — before/after evidence

No test pins the default sound w.r.t. `mod` (it is inaudible with FM/AM off — see §3), so there is
no default-sound before/after to produce; the distinction is empty.

For the state where `mod` **is** audible (FM engaged), the acceptance test `(d)` provides the
before/after: renders the drone3 channel with FM **ON** at depth 1.0 vs 0.5 and asserts the two differ
(`peakDiff > 1e-5`). That is the concrete before/after for the only state in which the knob matters.

## 6. Acceptance implementation (tests/core/test_machine_runtime.cpp)

A new D1 section, after the #46 ControlEvent dispatch block. 10 checks:

| id | check | pass |
|----|-------|------|
| (c) | fresh runtime `drone3ModApplied()==0.5` / `drone6ModApplied()==0.5` (registry default) | PASS |
| (a) | batch lane `applyDspParam(drone_3_mod, 0.8)` = `applied` + `drone3ModApplied()==0.8` (ditto drone_6) | PASS |
| (a')| norm→depth: `applyDspParam(drone_3_mod, 1.0)` → `drone3ModApplied()==1.0` (kModDepthFromNorm) | PASS |
| (b) | live lane: ControlEvent `drone_3_mod=0.8` @ sample 0 → `processBlock` → `drone3ModApplied()≈0.8` (`<1e-5`, float quantization of `SignalSample`) | PASS |
| (d) | render lever: FM **on**, `setDrone3Mod(1.0)` vs `0.5` → `drone3Channel()` `peakDiff>1e-5` | PASS |

**(b) tolerance note:** `ControlEvent.value` is `SignalSample` (float); `0.8` becomes `0.8000000119`,
so the live-lane assertion uses `std::fabs(x-0.8) < 1e-5`. The batch lane (`double`) keeps exact `== 0.8`.
The getter reads the **real** PapaVoice field (`modApplied()`), not a shadow bank, so (a)/(a')/(b)/(d)
all prove dispatcher→runtime→audio reachability on the actual render path.
