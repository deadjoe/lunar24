ANALYZER A/B -- does this slice's analyzer change move a byte of its own output?

What changed on the branch: tools/gh19_s3_pulse_analyze.py gains `--taps2`, so the reference
decimator's tap count can be set independently for the 2L level (`taps2 = args.taps if args.taps2 is
None else args.taps2`, then `design_decimator(taps2, ...)`). The claim under test is that with the flag
unset the analyzer's output is byte-for-byte what main produces.

Method: the same arm (/tmp/prb-pipe/cand) analysed by both revisions, at two flag sets, stdout
compared byte for byte. `--taps2` is never passed, so both runs take the `args.taps2 is None` path.

IDENTICAL on both, so the change is inert at the flag settings the slice actually uses.

Two things a reader should not misread:
  * exit=3 at the cheap flags is the analyzer's own status for a short-tap survey, identical on both
    revisions. It is NOT a failure of the comparison, and it is NOT the gate's RED (1) or REFUSE (4).
  * the two shas DIFFER BETWEEN FLAG SETS, as they must: a 65-tap, 8-cell survey is a different matrix
    from a 2001-tap, 56-cell one. The comparison is main-vs-branch WITHIN a flag set, never across.

Cost, for the budget in the report: the pinned pair is 559.04 + 565.92 = 1124.96 s of analyzer time for
one A/B. This leg is NOT part of the slice's test entries; it was run once, here.
